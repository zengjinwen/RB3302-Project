User explicitly clarified: even if AMCL reaches destination first, continue summing contributions; odom is more trusted for distance.
Per straight segment, record initial filtered odom position and fix route direction in the odom frame using the segment-start map/odom orientation. Project net odom displacement onto that axis. Compare with segment centre-to-centre length. Once length reached, odom contribution is latched off for the rest of that segment, including reverse recovery.
Before odom reaches length: +0.7*v in route direction. Afterwards: 0.
AMCL contribution: +0.3*v if behind destination along segment; -0.3*v if beyond; 0 if within existing 5cm 2D arrival radius.

At v=0.10: both short -> +0.10; AMCL at target, odom short -> +0.07; AMCL past target, odom short -> +0.04; odom done, AMCL short -> +0.03; odom done, AMCL beyond -> -0.03.

7. REVERSE PARTICLE BUG: INVESTIGATION AND CORRECTION
User observed robot reversing while RViz particles moved forward, then reported they appeared stationary. Initial assistant suspicion focused on raw base dist_centre sign and odom direction, without measured robot evidence. That was incomplete. Current base driver computes delta_dist from successive dist_centre values; actual firmware behavior during reverse has not been confirmed from signed feedback traces.
Reviewed upstream Navigation2 Jazzy DifferentialMotionModel::odometryUpdate. Original source sets delta_rot1=0 if translation magnitude <0.01 m, while delta_trans=sqrt(dx^2+dy^2) remains nonnegative. This creates a genuine forward prediction for small reverse steps. With 0.03 m/s reverse and ~8 Hz updates, nominal step is 0.00375 m, inside this branch.
A local C++ test linked against the installed upstream motions_lib reproduced: -0.00375 m odom input -> +0.00375 m particle translation (zero motion noise). This is measured local software evidence, not speculation.
First fix: custom plugin rb3302_amcl_motion, class nav2_amcl::RB3302DifferentialMotionModel. Small-step direction chosen from signed projection onto previous odom heading: negative -> pi, positive -> zero. All other upstream motion code initially retained. Config localization.yaml switched robot_model_type to custom class; mission package dependency added. No new runtime node, plugin loaded inside existing AMCL. Original license notices retained.
User reported problem persisted on robot. Exact loaded class, TF displacement and post-resampling cloud were NOT remotely confirmed; SSH attempt timed out. Do not state that robot was running a particular build just because upload commands were provided.
Second/latest fix, requested explicitly by user: replace the motion update with signed 2D displacement transformation for ALL step sizes; delete the 1cm special case. Convert odom delta dx/dy into previous robot-local forward/sideways components, rotate into each particle's map heading, and apply displacement. Zero odom translation and rotation returns unchanged, no injected motion noise. Pure rotation changes heading only. Translation noise changes magnitude with nonnegative scale, so it cannot flip direction. Heading noise retains alpha1/alpha2 variance, translation variance alpha3/alpha4. Clipping Gaussian displacement magnitude at zero introduces a small positive magnitude bias; this is a documented tradeoff, not a mathematically unbiased standard AMCL model.
Laser likelihood weighting/resampling were NOT changed. They change the particle distribution after prediction. AMCL reads odom TF at scan time, not cmd_vel or merely /odom.twist. Thus a negative /odom velocity alone is insufficient proof of what AMCL received.
